# Supabase Auth & Middleware Best Practices Report

## შეჯამება
თქვენი მიდგომა Supabase-ის ავტორიზაციასთან და Middleware-თან მიმართებაში **სწორია და შეესაბამება თანამედროვე სტანდარტებს** (Next.js App Router + Supabase SSR).

თუმცა, `autoRefreshToken: true` კლიენტის მხარეს, გარკვეულ სიტუაციებში (მაგ. iOS, Tab Switching), იწვევს კონფლიქტს და "უსასრულო ლუპს". მისი გამორთვა (`false`) არის რეკომენდებული გზა მსგავსი პრობლემების დროს, თუმცა ამას სჭირდება სწორი მენეჯმენტი.

ქვემოთ მოცემულია დეტალური ანალიზი და რეკომენდაციები.

---

## 1. Middleware-ის ანალიზი
**თქვენი კოდი:** `src/lib/supabase/middleware.ts`
*   ✅ **იყენებს `createServerClient`-ს:** ეს არის სწორი მეთოდი Cookie-ების სამართავად Next.js-ში.
*   ✅ **იყენებს `getUser()`-ს:** დოკუმენტაციის მიხედვით, Middleware-ში *აუცილებელია* `getUser()`-ის გამოყენება და არა `getSession()`-ის. `getUser()` ამოწმებს ტოკენის ვალიდურობას სერვერთან და უსაფრთხოა.
*   ✅ **Cookie Management:** სწორად ხდება Cookie-ების წაკითხვა და ჩაწერა (`request` და `response` ობიექტებში).
*   ✅ **Error Handling:** შეცდომის შემთხვევაში Cookie-ების წაშლა არის უსაფრთხო მიდგომა, რათა არ მოხდეს არასწორი სესიის შენარჩუნება.

**შენიშვნა ISR-ზე (Static Pages):**
თქვენს `middleware.ts`-ში არის ლოგიკა:
```typescript
if (isISRPage(pathname)) {
  return NextResponse.next()
}
```
ეს **კარგია პერფორმანსისთვის**, რადგან სტატიკურ გვერდებზე (News, Articles) არ ტვირთავს სერვერს ზედმეტი რექვესთებით.
*   **რისკი:** თუ მომხმარებელი 1 საათზე მეტ ხანს მხოლოდ ISR გვერდებზე იმოძრავებს, Middleware ვერ განაახლებს ტოკენს. ამ შემთხვევაში, სესიის განახლებაზე პასუხისმგებელი ხდება კლიენტი (Client Side).

---

## 2. Client Side Auth & `autoRefreshToken`
**პრობლემა:**
Supabase-ის კლიენტს (`createBrowserClient`) აქვს ჩაშენებული მექანიზმი, რომელიც ცდილობს ტოკენის განახლებას, როცა ის ვადაგასულია.
*   როდესაც `autoRefreshToken: true`, კლიენტი აკეთებს `POST /token?grant_type=refresh_token` რექვესთს.
*   თუ ეს რექვესთი ფეილდება (მაგ. ქსელის პრობლემა, ან ძველი `refresh_token`), კლიენტი შეიძლება შევიდეს "პანიკაში" და დაიწყოს უსასრულო ცდა (Retry Loop), რაც იწვევს `429 Too Many Requests` შეცდომას.
*   ეს განსაკუთრებით ხშირია iOS-ზე Safari-ს "Tab Sleep" რეჟიმის გამო.

**გადაწყვეტილება:**
`autoRefreshToken: false`-ზე გადაყვანა (რაც უკვე გავაკეთეთ) არის **სწორი ნაბიჯი** ამ ლუპის შესაჩერებლად.

**შედეგი:**
*   **დადებითი:** ლუპი შეჩერდება. საიტი სტაბილური გახდება.
*   **გასათვალისწინებელი:** კლიენტი ფონურ რეჟიმში აღარ განაახლებს ტოკენს. ტოკენის განახლება მოხდება მხოლოდ მაშინ, როცა:
    1.  მომხმარებელი გადავა ახალ გვერდზე (არა-ISR გვერდზე), სადაც Middleware იმუშავებს.
    2.  ან ჩვენ ხელით გამოვიძახებთ განახლებას.

---

## 3. რეკომენდაციები და გამოსწორების გზები

### რეკომენდაცია 1: დატოვეთ `autoRefreshToken: false`
ეს არის ყველაზე სტაბილური გზა. ნუ ენდობით Supabase-ის ავტომატურ რეფრეშს კლიენტის მხარეს, რადგან ის ხშირად იწვევს კონფლიქტს Middleware-თან (Race Condition).

### რეკომენდაცია 2: Middleware არის მთავარი
თქვენი არქიტექტურა სწორია - Middleware უნდა იყოს სესიის განახლების მთავარი წყარო. როცა მომხმარებელი დადის საიტზე, Middleware ანახლებს სესიას.

### რეკომენდაცია 3: AuthContext-ის გაუმჯობესება (Optional)
თუ მომხმარებელი დიდხანს (1 საათზე მეტხანს) გაჩერდება ერთ გვერდზე და არ გადავა სხვაგან, მისი ტოკენი შეიძლება გაუფასურდეს. რადგან `autoRefreshToken` გამორთულია, ის შეიძლება "ჩუმად" გამოვარდეს სესიიდან.

ამის თავიდან ასაცილებლად, შეგიძლიათ `AuthContext.tsx`-ში დაამატოთ მარტივი ინტერვალი, რომელიც პერიოდულად შეამოწმებს სესიას, მაგრამ არა აგრესიულად.

**მაგალითი (იდეის დონეზე):**
```typescript
// AuthContext.tsx
useEffect(() => {
  const interval = setInterval(async () => {
    const { data: { session } } = await supabase.auth.getSession()
    if (session) {
      const expiresAt = session.expires_at // timestamp
      const now = Math.floor(Date.now() / 1000)
      // თუ გასვლამდე დარჩა 5 წუთზე ნაკლები
      if (expiresAt - now < 300) {
        await supabase.auth.refreshSession() // ხელით განახლება
      }
    }
  }, 10 * 60 * 1000) // შემოწმება ყოველ 10 წუთში

  return () => clearInterval(interval)
}, [])
```
*ეს არ არის სასწრაფო, მხოლოდ მაშინ გააკეთეთ, თუ შეამჩნევთ, რომ მომხმარებლებს სესია უწყდებათ მუშაობის პროცესში.*

## დასკვნა
თქვენი სისტემა გამართულია. პრობლემა იყო მხოლოდ კონფიგურაციაში (`autoRefreshToken: true`), რომელიც იწვევდა კონფლიქტს.
1.  **Middleware:** ✅ მუშაობს სწორად.
2.  **Client Config:** ✅ `autoRefreshToken: false` არის სწორი არჩევანი.
3.  **Cookie Handling:** ✅ სწორია.

ამ ეტაპზე სხვა კრიტიკული ცვლილება არ არის საჭირო.
